# Veritas Atlas — complete product vision, prioritized feature and test backlog

**Planning baseline:** 2026-10-18 · **Status:** Proposed product-completion plan, not a verified implementation report or release authorization.

## 1. Product vision and boundary

Veritas Atlas is an **AI-assisted public-record intelligence platform** for finding, acquiring, verifying, comparing and presenting public-source evidence with defensible provenance. Users should be able to investigate a subject or question, inspect source-backed claims, identify contradictions, understand confidence/limitations, and publish only when evidence and governance gates permit. It is **not** a general ungrounded chatbot, a substitute for original records or an automated authority for legal/clinical/high-stakes decisions.

**Personas:** researcher/analyst (investigates, compares and cites); reviewer/editor (validates evidence and publication); authorized organization administrator (users, policies, source registry and audit); public reader (only approved published information). Initial single-operator staging is not equivalent to full multi-user production authorization.

**Normative references:** `README.md`, `docs/EVIDENCE_PROVENANCE_CONTRACT.md`, `docs/architecture/CITATION_INTEGRITY_MATRIX.md`, `docs/architecture/SOURCE_FRESHNESS_CONTRACT.md`, `docs/FIRST_RENDER_STAGING_DEPLOYMENT.md`, and project-owned CompanyOS trackers [#10](https://github.com/NTinkicht/veritas-atlas/issues/10), [#12](https://github.com/NTinkicht/veritas-atlas/issues/12). These contracts and their exact versioned fixtures govern detailed semantics. This document inventories desired capabilities; it **does not override or relax** those contracts, create WU leases, assign deployment authority or activate providers.

**Observed implementation caveat:** the canonical `apps/web/veritas-atlas-web/src/App.tsx` currently displays Vite sample UI, not the full analyst product. Database readiness exists separately from application/feature readiness. Do not mark a feature complete from documentation, fixture presence or a green generic build alone. Historical `_diagnostics/` evidence is not current source truth. Do not build in the legacy root `frontend/`.

## 2. Priorities and evidence statuses

- **P0 — trustworthy first complete product:** source authenticity, access control, defensible evidence/claims, real analyst workflow, exact build tests, safe staging and recovery.
- **P1 — full useful product:** richer research workflow, collaboration, robust publication, monitoring, performance and polished UX.
- **P2 — optional extensions:** additional connectors/models, advanced analytics and integration/export formats requiring their own approval.
- **Single mutually exclusive Status column, applied in precedence order:** (1) `VERIFIED`: *all* scoped behavior and required exact-revision tests/CI/review evidence satisfy acceptance, with no active delivery blocker; (2) `BLOCKED`: an unresolved external dependency prevents the next required step **even if some implementation exists**—record blocker ID, partial work and last known evidence separately; (3) `IMPLEMENTED_UNVERIFIED`: *all* feature behavior has evidence of implementation but required verification/review/release acceptance is incomplete, with no active blocker; (4) `PARTIAL`: some but not all required behavior is implemented with evidence, no active blocker; (5) `VERIFY`: suspected or reported implementation cannot yet be classified because exact source and tests have not been audited, no known active blocker; (6) `FUTURE`: not started and intentionally deferred optional P2; (7) `PLANNED`: not started or no verifiable implementation and not deliberately deferred. First matching state wins; no row may claim two states. If blocked after partial work use `BLOCKED` and link the partial evidence. If code is only partially implemented use `PARTIAL`, **not** `IMPLEMENTED_UNVERIFIED`, regardless of missing CI. Only `VERIFIED` counts toward release. These statuses do not create executable leases. Planned order is dependency-first within priority; never infer readiness from a roadmap alone.

## 4. Complete test program (required before claiming coverage)

1. **Unit and deterministic fixtures:** provenance reference/hash/URI normalization, pinned IDNA, source classification, parser versions, freshness and supersession, citation validation, confidence and contradiction rules.
2. **API and contracts:** full auth/access matrix, schema and pagination, malformed request handling, source allow-list and search filtering, immutable claims, state transitions and publication authority.
3. **Real PostgreSQL integration:** migration chain, transactional ingestion, duplicate and concurrent source updates, isolation, source version retention, investigation edits and recovery.
4. **Security/adversarial:** injection from public records never becomes instructions; SSRF and hostile redirects, malicious files, citation spoofing, parser version drift, prompt/data exfiltration, secret leak, CORS and cross-tenant IDOR.
5. **UI/E2E:** canonical Vite/React application, realistic query-to-publication journey across roles, empty/offline/slow paths, responsive widths, WCAG keyboard/focus/contrast checks and publication blocking.
6. **Performance/reliability:** ingest/search latency and throughput, large documents, queue saturation, external-source outage, graceful degraded behavior, resumability, restore/rollback drills.
7. **CI/release:** backend, frontend and container builds; deterministic tests on exact revision; actual separate staging resources, live/readiness probes and **feature** smoke; backup and release ledger, independent review.

A test fixture or markdown contract is **not** proof a product endpoint exists. Classify a row by the *first matching mutually exclusive rule* in §2; attach issue ID, blocker ID (when applicable), partially implemented features, source commit, test files, CI run, eligible independent review and residual risks in its evidence record. A blocked partial implementation is `BLOCKED`, not `PARTIAL`; complete code lacking CI is `IMPLEMENTED_UNVERIFIED`, not `PARTIAL`. None of the initial `VERIFY`/`PLANNED`/`FUTURE` rows is verified without exact source/test evidence.

## 5. Execution dependency chain and definition of done

**Phase A — prerequisites:** VER-P0-01–03 define trust/access and implement **baseline durable PostgreSQL storage** first. VER-P0-03 must pass migration, atomic evidence-store and tenant-isolation tests **before** VER-P0-05 ingestion, VER-P0-07 parser/index persistence and VER-P0-10 workspace CRUD are admitted; VER-P0-04–08 then establish source governance, ingestion, provenance and freshness. **Phase B:** VER-P0-09–15 deliver evidence search, research workspace, claims, contradictions and grounded intelligence; historical claim policies must be tested with required user-visible historical date and non-current-state labels. **Phase C:** VER-P0-16 establishes the **durable review/publication lifecycle and authorized API before** VER-P0-17's analyst UI integrates it. VER-P0-18 performs *later* retention, migration and recovery hardening after baseline/feature storage exists (not prerequisite initial persistence). **Phase D:** VER-P0-19–20 cover staging and adversarial end-to-end acceptance. **Phase E:** P1 enhanced product. **Phase F:** individually approved P2 extensions.

Each WU needs an approved bounded scope, explicit acceptance criteria, source and test files, and its own issue/PR unless already covered by a merged PR. The project backlog remains in **this** repository: OneCompany stays generic and must not take over Veritas's operational deployment identity, credentials or release decisions. Reconcile historical L4/L5 governance docs with simplified-current GitHub gates before admitting a writer. One canonical PR per implementation WU; CI green on exact head/base as required, eligible independent nonauthor review, all actionable findings resolved. No extra spend, provisioning, production deploy or destructive schema change is authorized here.

**Release exit:** a user can complete a real synthetic public-record investigation without using Vite demo UI or manual DB manipulation; every evidence-required claim is source-traceable; freshness-required current-state reports with stale/unknown/superseded evidence fail closed, policy-permitted historical reports disclose both their non-current evidence status **and the original claim's historical as-of/effective date context in the user-visible answer**, and spoofed, tampered and unauthorized reports fail closed; verified staging recovery/runbooks exist; product and security tests pass at exact revisions. Any external publication or production release requires its separately recorded authorization.
